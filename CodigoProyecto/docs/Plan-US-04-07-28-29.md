## US-04 + US-07 — Generación de Vuelos

### Modelo de datos (sin cambios)
`Route` → `SalesPeriod` (rango + avión + capacidad + tarifas) → muchos `Flight` (uno por fecha real). Campos exactos ya en `prisma/schema.prisma`:
- `SalesPeriod`: `routeId`, `startDate`/`endDate` (`@db.Date`), `airplaneId`, `economyCapacity`/`firstClassCapacity`, `economyFare`/`firstClassFare` (`Decimal`), `createdById`.
- `Flight`: `code` (único), `routeId`, `salesPeriodId`, `date` (`@db.Date`), `departureAt`/`arrivalAt` (`DateTime` completo), `airplaneId`, capacidad/tarifas propias (copiadas del período), `status` (`SCHEDULED`/`CANCELLED`), `createdById`. `@@unique([routeId, date])` ya impide duplicar un vuelo del mismo trayecto en la misma fecha; `@@index([airplaneId, departureAt])` ya está pensado para la validación de superposición.

### Nueva feature: `features/flights/`

**`generation.ts`** — helpers puros (sin Prisma), testeables directo:
- `matchingDates(startDate: string, endDate: string, operatingDays: DayOfWeek[]): Date[]` — itera día a día en UTC (`"YYYY-MM-DDT00:00:00.000Z"`) y devuelve las fechas cuyo día de semana está en `operatingDays`.
- `buildFlightWindow(date: Date, departureTime: string, arrivalTime: string): { date, departureAt, arrivalAt }` — combina fecha + horario; reusa `isNextDayArrival` de `@/features/routes/time` (ya existe y está testeado) para sumar un día a `arrivalAt` cuando corresponde. **No reimplementar** esa lógica.
- `windowsOverlap(a, b): boolean` — `a.departureAt < b.arrivalAt && b.departureAt < a.arrivalAt` (superposición de intervalos, sin contar como choque un aterrizaje justo cuando sale el otro).

**`schema.ts`**:
- `generateFlightsFormSchema`: `routeId`/`airplaneId` (`idSchema("Route")`/`idSchema("Airplane")`), `startDate`/`endDate` (string `YYYY-MM-DD`, regex), `economyCapacity`/`firstClassCapacity` (`z.number().int().min(0)`), `economyFare`/`firstClassFare` (`z.number().positive()`). Refines: `endDate >= startDate` (comparación de string funciona, mismo formato que `routeFormSchema`/`airportFiltersSchema` en fechas), y "al menos una clase con capacidad" (mismo patrón que `airplaneFormSchema`).
- `flightFiltersSchema`: `fecha` (string `YYYY-MM-DD` opcional), `origen`/`destino` (id de aeropuerto), `estado` (`"SCHEDULED" | "CANCELLED" | "todos"`, default `"SCHEDULED"` — mismo criterio que "activos" por defecto en el resto de los listados), `page`.

**`service.ts`** — `generateFlights(data, createdById: string): Promise<ActionResult<{ salesPeriodId: string; count: number }>>`:
1. `route = prisma.route.findUnique(routeId)`; si no existe o `!isActive` → error.
2. `airplane = prisma.airplane.findUnique(airplaneId)`; si no existe o `!isActive` → error.
3. `dates = matchingDates(...)`; si vacío → error ("el período no contiene fechas que coincidan con los días de operación").
4. `windows = dates.map(d => buildFlightWindow(d, route.departureTime, route.arrivalTime))`.
5. Buscar vuelos ya existentes del trayecto en esas fechas (`prisma.flight.findMany({ where: { routeId, date: { in: dates } } })`); si hay alguno → **rechazar todo**, informando cuántas fechas ya tenían vuelo.
6. Buscar vuelos `SCHEDULED` del avión que se solapen con el rango `[min departureAt, max arrivalAt]` de los candidatos (una sola query acotada por ese rango, aprovecha `@@index([airplaneId, departureAt])`), y chequear `windowsOverlap` contra cada uno **y** entre los propios candidatos (por si el propio período se pisa a sí mismo). Si hay algún solapamiento → **rechazar todo**, informando el avión y la fecha en conflicto.
7. `prisma.$transaction`: crea el `SalesPeriod` (`newId("SalesPeriod")`) y, para cada ventana, un `Flight` (`newId("Flight")`, `code = "VU-" + YYYYMMDD(date) + "-" + route.code.replace("TR-","")` — único por construcción gracias al `@@unique([routeId, date])`, sin necesidad de contar vuelos existentes de otros trayectos en la misma fecha).
8. Devuelve `{ salesPeriodId, count: windows.length }`.

**`queries.ts`** — `listFlights(rawFilters)`: mismo patrón que `listRoutes`/`listAirplanes` (filtro + paginación, `PAGE_SIZE = 10`), con `include` a `route` (código, aeropuertos origen/destino) y `airplane` (identificador). Cupo disponible = `capacidad - ocupado` por clase (igual fórmula documentada en el modelo de datos). `getSalesPeriodSummary` no hace falta: no hay pantalla de períodos, solo el listado de vuelos (igual que el wireframe).

**`actions.ts`** — `generateFlightsAction(values)`: `requireAdmin()` (guarda el `User` devuelto), `safeParse`, `flightsService.generateFlights(parsed.data, admin.id)`, `revalidatePath("/admin/vuelos")` si `ok`.

**`components/`**:
- `generate-flights-form.tsx` (client, RHF + zodResolver): tres bloques igual que el wireframe (trayecto+período, avión+capacidad, tarifas). Recibe `routes`/`airplanes` como props (ver queries nuevas abajo) con toda la data necesaria para no pedir nada más al server:
  - Select de trayecto (Base UI `Select` con `items` — **importante**: como se descubrió en el sprint anterior, `Select.Value` de Base UI necesita el prop `items` (`{value, label}[]`) para mostrar la etiqueta en vez del id crudo; ya se aplicó ese fix en `route-form.tsx`, replicar acá desde el principio.

  - Preview en vivo: con `routeId`+`startDate`+`endDate` completos, usar `matchingDates` (import directo, es una función pura) sobre los datos del trayecto ya presentes en `routes` para mostrar "Se van a generar N vuelos" (o el aviso de 0 fechas), replicando el texto de impacto del wireframe sin pedir nada al servidor.
  - Sin modo edición (esta pantalla solo genera, no hay período existente que cargar): botones "Generar y Publicar Vuelos Reales" + "Restablecer Formulario" (se omite "Previsualizar Calendario" del wireframe — el preview en vivo ya cubre esa necesidad sin construir un modal de calendario aparte, fuera de lo pedido por los criterios de aceptación).

## US-28 + US-29 — Registro, Login/Logout (cierre de brecha)

### `lib/auth.ts` — extraer `syncClerkUser` (refactor, mismo comportamiento)
```ts
export async function syncClerkUser(clerkId: string): Promise<User | null> {
  const existing = await prisma.user.findUnique({ where: { clerkId } });
  if (existing) return existing;

  const clerkUser = await currentUser();
  if (!clerkUser) return null;

  const email = clerkUser.emailAddresses.find(e => e.id === clerkUser.primaryEmailAddressId)
    ?.emailAddress ?? clerkUser.emailAddresses[0]?.emailAddress;
  if (!email) return null;

  return prisma.user.create({
    data: { id: newId("User"), clerkId, email, firstName: clerkUser.firstName ?? "", lastName: clerkUser.lastName ?? "" },
  });
}

export const getCurrentUser = cache(async (): Promise<User | null> => {
  const { userId } = await auth();
  if (!userId) return null;
  return syncClerkUser(userId);
});
```
`getCurrentUser` sigue memoizado con `cache()` (no cambia su comportamiento ni su firma); `syncClerkUser` es una función plana normal, importable y testeable sin pelear con el cacheo de React entre tests (a diferencia de `requireAdmin`, que en el sprint anterior se dejó sin testear directamente por esa misma razón — acá si se puede, porque no depende de `redirect`/`forbidden`).

**`lib/auth.test.ts`** (agregar al archivo existente): mock de `currentUser` de `@clerk/nextjs/server` + `prismaMock` ya existente. Casos: usuario ya existe → lo devuelve sin llamar `currentUser()` ni `user.create`; no existe y Clerk tiene email primario → crea con id `USU_...` y los campos mapeados; no existe y `currentUser()` es `null` → devuelve `null`; no existe y no hay `primaryEmailAddressId` pero sí `emailAddresses[0]` → usa ese; no existe y no hay ningún email → devuelve `null` sin crear.
